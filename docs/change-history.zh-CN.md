## 1. test-05：把可独立判断的事实分开

原 gold 的 g1 同时包含 HTTP 200 和 JSON body，g2 表示无需认证。模型若正确输出三条原子事实，旧的一对一对齐会把其中一条算成多余预测，评分偏低。修复的是评分依据，不能把分数变化称为模型能力提升。

修改后为三条 SUPPORTED：

| 稳定 ID | 事实 | 理由 |
|---|---|---|
| g1 | GET /status returns HTTP 200. | 缩小原 g1，保留主体和状态码 |
| g3 | GET /status returns a JSON body. | 新增独立可核验的响应格式断言 |
| g2 | GET /status requires no authentication. | 保留原 ID，避免旧 g2 被换成另一含义 |

状态码与响应格式取原文第一句作证据。认证事实保留完整段落，包含 “This endpoint” 的指代对象。原文、生成答案和 verdict 不变。ID 是身份，不是排序，因此存储顺序为 g1、g3、g2。

优点是无需引入复杂的多对多匹配，也能公平比较原子拆解。代价是必须修改数据版本并重做受影响的审查。仍然这样选，是因为放宽匹配容易掩盖重复事实或遗漏；这里有清晰、局部、可解释的 gold 修复。

回归使用人工构造的合成输出：正确三条得 F1=1；正确复合输出经审阅切分也得 F1=1，但原子性为 0；漏掉 JSON body 仍有一个 FN、F1=0.8；重复 body 仍有一个 FP。这些不是模型实验结果。

## 2. 具体判定理由：让每个标签都能被质疑

为修改后的全部 44 条 gold 编写英文 `reasoning` 和 `annotation_reason`。前者解释材料如何支持、排斥或未能确立断言；后者解释标注决策，例如必要限定条件、原子粒度或为什么不能选另一个标签。

SUPPORTED 要写出有效推导；多段落案例交代完整证据链。CONTRADICTED 要指出同一条件下不兼容的数量、极性或配置。UNSUPPORTED 要说明缺少什么信息或前提，不能把“没有提到”写成“明确反对”。例如 test-06 区分 30 与 31 天，test-18 保留 secure-mode 前提，test-19 说明二状态下 12−7=5 的推导。

优点是人工复核能检查推理，而非只看标签；缺点是解释也可能写错，而且解释变更会改变当前严格数据哈希。仍选择逐条补写，是因为小样本项目的可信度主要来自可审计的判断；模板不能替代判断。解释均为 Codex 草稿，仍需你批准，未自动改 manifest 的审核或冻结状态。

## 3. 完整审阅文档：从唯一数据源生成

你已删除 Canvas，因此本次用 [完整 Markdown 审阅文档](../reviews/gold-dataset-review.md) 承接审阅需求，不恢复 Canvas。生成器展示 28 个案例的全部元数据、原始上下文及索引、生成答案、每条 claim 的 ID、文本、verdict、两种理由和完整引用，以及 manifest、派生计数与规范化数据哈希。

命令 `python -m grounding_verifier.cli gold-review` 从 JSONL 和 manifest 重新生成。`--check` 逐字比较当前生成结果，缺失或过期都会失败，已加入离线 CI。修改数据中的解释、引用或审核状态后，需要重新生成。生成文档本身不会批准 gold 或冻结 test。

优点是 GitHub、编辑器和离线环境都能阅读，少一个手工维护的数据副本；缺点是文档较长，没有 Canvas 的筛选交互，也没有在页面上直接批准的能力。当前只有 28 个案例，完整字段和可复现比额外 UI 更有价值，因此接受这个代价。原始文本使用代码围栏保留格式，说明文字转义 Markdown 控制符。
